## localStorage依存

| キー | 用途 | 移行時の扱い |
|---|---|---|
| usglass_projects | 旧案件一覧 | コピーして移行。削除しない。既存Driveデータがある場合も、ID照合・内容比較・重複確認が必要 |
| usglass_GP / usglass_CR / usglass_OTHER | 実務用マスター | 端末の原本をバックアップし、案件に適用された単価も記録 |
| usglass_CR_schema | 工賃マスター移行版 | 金額の履歴とは別物。新しい価格ルールのバージョンとして流用しない |
| usglass_default_sell_mult | 既定の材料倍率 | 新旧価格ルールに分けて保存。旧値を黙って上書きしない |
| usglass_google_client_id | Google接続用設定 | 認証設定として分離。アクセストークンは現在メモリ保持 |
| usglass_last_drive_sync | 最終同期表示 | 現在の入力が保存済みである証明には使えない |
| ORDER_SHEET_LS_KEYに指定されたキー | 注文表アプリへの受け渡し | クラウド保存と独立した互換性を維持 |

Drive直接保存では旧同期ボタンが無効化され、保存時に最新のGP/CR/OTHERを収集しない。既存DriveファイルのmasterPricesは残るが更新されない。端末を変えて案件を読み込んだ際に、単価が自動的に一致する構造ではない。

## 正式新ルールと現行差異

価格定義の唯一の根拠は今回のユーザー指定。リポジトリ内の0や旧単価を機械的に2倍にしない。

| 項目 | 現行 | 新ルール / 対応 |
|---|---|---|
| 通常材料 | 平米単価×面積×枚数×1.10を丸め、材料倍率（既定2.0）を適用 | 材料原価×1.5。通常の1.10を除く新価格処理が必要 |
| 修理材料 | 新築/修理の専用区分なし。通常にも1.10が掛かる | 修理を明示選択した場合に1.10×1.5 |
| ミラー材料 | 通常ガラス同様に1.10×材料倍率 | 材料原価×1.5 |
| 施工 | 単価×面積×枚数。行の手入力単価が優先 | 指定の完成単価をそのまま使う。追加の×2なし |
| 修理施工 | 修理専用倍率・修理区分なし | 未確認の修理追加倍率を作らない。取り外しとは別項目 |
| 取り外し | 施工費と同額を加算 | 維持 |
| ミラー施工 | OTHER.mirrorLabor×枚数 | 単価10,000円は確定。1枚/1明細/1現場のどれに固定するか要確認 |
| コーキング | (W+H)/1000×両面4または片面2×枚数。行単価優先 | 基本350、防火750、剥がし300。ビード0を維持。独立した「なし」を追加予定 |
| 元請け材料 | 社内材料売価×1.25が既定 | 新価格に旧倍率を重ねない。新価格では基本1.0を想定し、得意先調整とは分ける |
| 元請け施工 | 施工・取り外し×1.75が既定 | 新施工価格に旧倍率を重ねない。新価格では基本1.0 |
| 元請けコーキング | コーキング・剥がし×1.48が既定 | ユーザー指示どおり勝手に変更しない。社内単価350/750と提出倍率は区別する |
| NET→見積 | 手入力やNET×別倍率（既定1.25）も選択可能 | 材料倍率と別の仕組み。旧見積では維持。新規は二重適用しない既定モードと説明が必要 |
| 自動諸経費 | 数量1～3:7500、4以上:15000 | 今回変更指示なし。維持し、将来管理設定に分離 |
| 廃棄 | OTHER.disposal×枚数 | 指定1000を定義。既存の枚数単位は未変更 |
| 戸車 | マスターにdoorPulleyがあるが専用計上処理は見当たらない | 指定2000を定義。UIへの接続は後続 |
| 送料 | 追加費用の原価/売上フラグで表現可能。ただし実NET粗利に原価分が反映されない | 新価格では原価＝売上、社内・NET双方で粗利0を検証する必要 |

固定の1.5は新規の基本材料倍率。得意先別設定や既存の明示的な売価入力は削除しない。新規の標準と個別調整を区別し、表示・保存する。

丸めの順序は現行の明細単位の丸めを基本にする。変更する場合は金額差を示す。通常材料へ1.5だけ入れてもFL5 1㎡は2822円になり、1710×1.5の2565円にはならない。施工単価だけを2000へ変えても元請け表示は3500円になる。この差異をテストで明示している。

## 旧見積を守る適用設計

1. 単価変更前に端末の旧マスター・既定倍率・旧案件をコピーしてバックアップする。原本は削除しない。
2. 新規案件は計算ルール版と単価スナップショットを持つ。旧案件は自動的に新価格へ切り替えない。
3. 単価スナップショットがない旧案件は、保存時の金額を完全には再現できない。現行端末の値で基準を作ったことを明示し、元のPDFとの照合が必要。
4. 新規への複製で旧価格を維持する操作と、新価格で再見積する操作を区別する。
5. 保存するデータに入力、設定、単価、計算版、算出総額、粗利をまとめ、読込で他案件の単価や端末マスターを書き換えない。
6. 計算ロジック変更PRとUI変更PRを分ける。旧価格回帰ケースと新価格ケースの両方を実行する。

現時点ではこの設計は未実装。承認済み単価のJSONを本体へ読み込ませるだけの変更は行っていない。

## クラウド保存の次段階

既存Google Drive認証・フォルダを活かす。新サービスやAI APIを導入する前提はない。

- 全件ファイル更新のままでは端末間の更新を失う。案件単位の保存と履歴の追加保存、保存前の版照合を設計する。単純な読込→更新だけを競合対策と呼ばない。
- 入力直後は端末の下書きへ退避し、遅延付きクラウド自動保存を行う。未接続・通信失敗時の下書きがあることを表示し、確認できる再送を行う。
- 保存成功前に現在案件IDや保存済み表示を確定しない。別案件読込・削除・複製との競合を防ぐ。
- 壊れたデータを空データに直して書き戻さない。原本を保護して復旧導線を出す。
- ゴミ箱、履歴、バックアップと復元を用意する。JSON構造版と計算ルール版は別管理。
- 既存localStorage→Driveの移行はプレビュー・件数照合・二重実行防止・復元手段を持つ。実データの削除や一括置換はしない。
- 検索対象は現場・宛先・日付・品番・ガラス・寸法・金額・ステータス。フィルタUIは保存形式が固まってから追加。

## 検証限界

テスト用単価は明示的に与えた仮の値。実際のブラウザマスターや顧客見積の保存時の値を取得したものではない。

Google Driveテストはメモリ上の代替処理。実認証、OAuthポップアップ、実通信、同時編集の競合防止、端末内の保存容量不足、iPhone実機、PDFレイアウトの検証はまだ行っていない。構文検査だけでUI動作やPDF品質の合格とはしない。
